# 开发任务

所有任务围绕本地研究工具包展开。交付范围是用户本机运行的工具包。[实施记录](implementation-status.md)

表中 T01 至 T14 是能力拆分；实际编码按 [Vibe coding 执行计划](vibe-coding-plan.md) 的 V00 至 V11 逐轮推进：先核实上游边界，再完成 CPU 闭环，尽早接入真实环境。Docker、复杂缓存和报告按真实需求补齐，不必一次完成整层才验证下一层。

## 里程碑与执行顺序

- **M0：T01 至 T07 的最小链路。** 假环境和假 policy 足以验证配置、进程通信、取消与文件结构；不依赖 GPU。
- **M1：T08、T09。** RoboDojo 的 eval-only 版本与官方入口对照证据。先用无权重 smoke 验证两条运行路径，再以 π0 对照。完整任务范围的验收在 V08 收口。[官方入口对照协议](integrations/robodojo-comparison.md)
- **M2：T10 至 T12。** 本地报告、第二个 benchmark 和比较／复现能力。第二个插件用于检验边界是否真正可复用。
- **M3：T13。** 形成研究版本和可复现实验；再按 B03、B04 等一次一个继续集成。
- **可选：T14。** Training 既不阻塞 M1，也不是扩大 benchmark 覆盖的条件。

T04 优先复用现有 NativeRuntime 和模型的独立解释器。长期以每个 benchmark 的 Docker 配方作为交付默认，V05 用 RoboDojo 上游脚本验收容器，验证后接入该插件的 `prepare`。后续 benchmark 提供可复用场景时再抽象通用容器运行后端。若 B01 的上游依赖或资产不可获得，记录阻塞原因并选择可验证的首个 benchmark，保持插件边界。

## 每新增一个 benchmark 的独立任务模板

1. 固定上游 revision 与原生基线，确认协议、许可、硬件和资产可得性。
2. 编写隔离环境配方、prepare／doctor、资产清单与缓存。
3. 定义 I/O profile、原生 runner 和最小 adapter 示例。
4. 解析评分，采集轨迹／视频／调用，补异常 fixture。
5. 自备 GPU 实测原生入口与工具包入口，记录准确命令、时延、资源和差异。
6. 提交 README、支持矩阵和验收记录，再标记状态。

详见 [集成规范](benchmark-integration.md)。每个插件独立合入；没有 GPU 验收证据不能用 CPU fixture 代替 ready。

## 研究验证任务细化

T13 的实验材料至少覆盖以下内容，并公开原始测量，不能预先写提升数字。

| 实验 | 对照和控制 | 应记录的结果 |
| --- | --- | --- |
| 官方协议对照 | RoboDojo 官方入口与 OpenPlatform，固定共同版本、checkpoint、实际布局和模型配置 | 调用／控制／终止差异，原生指标、各自分母、覆盖与随机波动，记录不可配对项 |
| 执行开销 | 两路采集范围尽量对齐，另测 OpenPlatform 诊断采集开关 | wall time、调用延迟分布、显存峰值、磁盘与控制时序变化 |
| 接入成本 | 固定模型与 benchmark 范围，对比手工官方接入与 OpenPlatform | 首次／后续接入耗时、代码量、步骤、错误，记录操作者经验和复用基础 |
| 可扩展性 | B01 后新增 B02，再至少分析一个不同环境需求 | 核心变更、插件独立代码、协议例外；抽象失效也属于发现 |
| 跨机器复现 | 两台已列支持范围的用户机器、冻结配置 | 安装成功率、准备时间、版本／结果差异与不可复现项 |
| 分析可用性 | 选定分数相同但轨迹不同、任务失败、提前终止和运行故障案例 | 从各路产物能否找到首个可观测差异、诊断耗时与缺失字段 |

真实分数和性能实验需要自有或合作方机器。CPU CI 检查 schema、codec、mock plugin、原始结果解析、状态恢复和报告生成；GPU 测试按插件标记手动运行，输出版本和硬件记录。先完成必要检查，未修改相关行为时不重复扩大测试范围。

## 发布要求

README 明确当前可用插件、命令与硬件范围；未知模型能力不承诺。示例全部为真实可解析配置；跑过的 recipe 固定 revision／锁文件。提供从 clone 到单 benchmark 结果的复现命令，列出下载、磁盘和 GPU 需求。维护者不需要部署 API、数据库或常驻评测机器。
